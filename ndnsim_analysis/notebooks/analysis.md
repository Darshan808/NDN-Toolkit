# NDN Intrusion Detection — ndnSIM Analysis

## Overview

This project implements **unsupervised per-node anomaly detection** on NDN (Named Data Networking) traffic logs generated by ndnSIM simulations. The objective is to detect two common NDN attack types:

- **IFA (Interest Flooding Attack)**
- **CP (Content Poisoning)**

The detection pipeline operates without attack labels during detection and evaluates attack behavior across three different network topologies.

## Raw Data

Each simulation run generates four trace files.

| File                                 | Description                                        |
| ------------------------------------ | -------------------------------------------------- |
| `{topo}-{scenario}-rate-trace.txt`   | Per-node packet counters and forwarding statistics |
| `{topo}-{scenario}-cs-trace.txt`     | Cache hits and cache misses                        |
| `{topo}-{scenario}-app-delays.txt`   | Packet delay, retransmissions, and hop counts      |
| `{topo}-{scenario}-ground-truth.csv` | Timestep-level scenario labels                     |

# Notebook 1 — Data Preprocessing

**File:** `01_preprocessing.ipynb`

This notebook loads raw ndnSIM trace files, performs feature engineering, and exports processed datasets.

## Processing Pipeline

1. Parse rate-trace files
2. Parse content store traces
3. Parse application delay traces
4. Parse ground truth labels
5. Pivot traces into one row per:

```text
(Time, Node)
```

6. Automatically determine consumer and router nodes
7. Compute behavioral features
8. Export processed CSV datasets

---

## Engineered Features

| Feature              | Description                           |
| -------------------- | ------------------------------------- |
| `cache_hit_ratio`    | CacheHits / (CacheHits + CacheMisses) |
| `satisfaction_ratio` | InSatisfiedInterests / InInterests    |
| `timeout_ratio`      | InTimedOutInterests / InInterests     |
| `nack_ratio`         | InNacks / InInterests                 |
| `interest_amp`       | OutInterests / InInterests            |
| `data_ratio`         | InData / OutInterests                 |
| `InInterests`        | Raw incoming interests                |
| `OutInterests`       | Raw outgoing interests                |
| `InData`             | Raw incoming data packets             |
| `delay_mean`         | Mean end-to-end delay                 |
| `retx_mean`          | Mean retransmission count             |

# Notebook 3 — Anomaly Detection

**File:** `03_detection.ipynb`

This notebook implements and evaluates an unsupervised per-node anomaly detector.

---

## Detection Approach

### Baseline Construction

For each node:

- Use the first 200 seconds of monitoring data.
- Compute feature mean and standard deviation.

No attack labels are used.

### Detection Features

- `satisfaction_ratio`
- `timeout_ratio`
- `cache_hit_ratio`

### Z-Score Computation

At every timestep:

```text
mean_z = average(feature z-scores)
```

Flag a timestep when:

```text
mean_z > 2.5
```

### Persistence Filter

To reduce noise:

```text
anomaly_score =
(fraction of flagged timesteps within
last 3 samples) × 100
```

Raise an alarm when:

```text
anomaly_score > 50
```

---

## Model Variants

### Global Model

Single baseline trained using normal traffic from all topologies.

### Per-Topology Model

Separate baselines trained for:

- DFN
- Dumbbell
- Tree

individually.

# Evaluation Methodology

## Why Precision and Recall Are Not Reported

The available ground truth labels entire simulation timesteps as attack or normal.

However:

- The attack originates from a specific node.
- Only neighboring nodes are directly affected.
- Many distant routers remain unaffected.

Consequently, labeling every node as attacked after `t = 301` would produce misleading precision and recall values for a per-node monitoring system.

Instead, evaluation focuses on:

### Temporal Lift

Does anomaly score increase after attack onset?

### Per-Node Localization

Which nodes are identified as abnormal?

### Detection Latency

How quickly is the attack detected?

### False Alarm Rate

How often are alarms raised during normal traffic?

# Related Work

This study mirrors the structure of a companion miniNDN-based intrusion detection project that employed:

- PIT size
- PIT growth rate
- Content Store size

as primary features and used Isolation Forest for anomaly detection.

Because ndnSIM tracers do not expose PIT or Content Store state directly, this work derives behavioral indicators from available forwarding and cache statistics and employs a lightweight z-score persistence detector that better captures the abrupt step-change characteristics observed during Interest Flooding and Content Poisoning attacks.

# Summary

This repository presents a complete workflow for NDN intrusion detection using ndnSIM-generated traffic:

1. Trace parsing and feature engineering
2. Exploratory analysis of attack behavior
3. Unsupervised per-node anomaly detection
4. Evaluation using temporal lift, localization, latency, and false alarm rates

The approach requires no attack labels during detection and successfully identifies both Interest Flooding and Content Poisoning attacks across multiple NDN topologies.
